# ДЗ4. Дежурный по репозиторию «Ромашка»

Агент помогает разработчику магазина разбирать issues: отвечает на вопросы, отличает баги от новых функций и исправляет код через PR. Успех — исправление проходит тесты проекта, новый тест воспроизводит баг на исходном коде, а независимая приёмка подтверждает результат.

Схема: issue -> триаж -> кодер в Docker -> тесты -> ревьюер -> подтверждение человеком -> PR. Вопросы получает ответчик, для остальных типов используются метки и короткие комментарии.

## Запуск

После клонирования скопировать `.env.example` в `.env` и заполнить три значения:

```dotenv
OPENROUTER_API_KEY=свой_ключ
GITHUB_TOKEN=свой_токен
GITHUB_REPO=владелец/репозиторий
```

Запуск одной командой:

```bash
make run
```

Результаты сохраняются в `results/run_*.csv`, журнал — в `results/calls.jsonl`.

Другие режимы:

```bash
make run ARGS="--check"                 # GitHub и тесты в Docker, без моделей
make run ARGS="--mode ask"              # подтверждение каждой записи в GitHub
make run ARGS="--compare"               # три конфигурации на открытых issues
```

## Репозиторий

Используется [Dravner/romashka-duty](https://github.com/Dravner/romashka-duty): 10 задач, из них 6 багов. Приёмочные тесты находятся отдельно, в `data/acceptance/`, и не передаются кодеру. `template/` содержит исходный магазин с багами и обычными тестами; `data/issues.json` — задачи и эталоны для оценки.


## Результаты

Один сравнительный прогон на 10 задачах до слияния первого исправления. Сейчас issue №1 закрыта, поэтому повторный запуск на текущем GitHub даст другой набор открытых задач.

- Sonnet без ревьюера: одна Sonnet выполняет триаж, исправление и ответы, отдельного модельного ревьюера нет.
- Команда: Haiku делает триаж, Sonnet исправляет, mini проверяет и отвечает.
- Всё на mini: все роли выполняет mini.

Ложный PR — внутренние проверки пропустили правку, а внешняя приёмка её отвергла. Во время сравнения настоящие PR не создавались: использовался `dry`.

Команда и Sonnet исправили все баги. Команда оказалась немного дешевле, но одного прогона мало для уверенного вывода о такой небольшой разнице. Mini дешевле за исправленный баг, однако исправила только два из шести.

## Проверка проверки

У mini исправление промокода в issue №1 прошло внутренние проверки и ревью, но не прошло внешнюю приёмку. Это один ложный успех; в итоговое число исправлений он не включён. Дифф именно этой попытки не сохранился, поэтому точная причина не установлена.

В issue №9 mini выбрала `bug` вместо `needs_info`: в сообщении недостаточно сведений для воспроизведения ошибки. Полный ручной разбор всех решений не проводился.

Отдельно проверен настоящий [PR №11](https://github.com/Dravner/romashka-duty/pull/11): нормализация промокода через `strip().upper()` и новый тест. Все 23 теста и внешняя приёмка проходят; новый тест на исходном коде падает. PR создан с подтверждениями и слит в `main`.

## MCP и ограничения расходов

GitHub MCP работает по HTTP, песочница — по stdio. Кодеру доступны 6 инструментов работы с файлами и тестами, ответчику — 2 инструмента чтения GitHub. Записи выполняет отдельная обвязка.

| Набор GitHub | Инструментов | Налог mini, токенов на вызов | Налог Haiku |
|---|---:|---:|---:|
| Дежурный | 9 | 2235 | 4265 |
| Ответчик | 2 | 375 | 1088 |

Белый список уменьшил налог на 83% у mini и на 74% у Haiku. [График](results/img/tax.png). Описания и схемы GitHub проверяются по отпечаткам в `pins.json`; налог песочницы отдельно не измерялся.

Порог расходов на задачу — $0.15, не более 16 шагов в одном агентном цикле и двух попыток исправления. Это мягкий порог: последний запрос и ревью могут увеличить сумму. `spent_today()` считает расходы за день по журналу в часовом поясе Москвы. Журнал содержит модель, токены, стоимость, время и запрошенные моделью инструменты.

## Безопасность

У агента есть доступ к приватному коду, недоверенным текстам issues и операциям записи. Выполнение кода отделено от секретов и сети: контейнер работает не от root, с `--network none`, ограничениями памяти, CPU и процессов. Корневая файловая система доступна только для чтения; запись разрешена в рабочей копии и временной папке. Ключи в контейнер не передаются.

Токен GitHub ограничен одним учебным репозиторием: Contents, Issues и Pull requests — чтение и запись; Metadata — чтение. Эти права нужны для чтения кода, создания веток, PR, комментариев и меток. Workflows не требуется при обычной загрузке шаблона. Ключ OpenRouter используется только HTTP-клиентом. `.env` исключён из Git, ключи не добавляются в сообщения модели.

В `dry` записей нет. В `ask` человек видит полные аргументы каждой операции и подтверждает её; отказ прекращает выполнение. Автоматического слияния PR нет. Текст issue не даёт дополнительных прав: модель вызывает только разрешённые инструменты. Полной защиты от prompt injection нет, поэтому дифф и аргументы перед записью нужно читать.
